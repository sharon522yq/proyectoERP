# Decisiones y supuestos

Fecha: 2026-10-05.

1. Se conserva Express/Mongoose y Expo. No había integración comercial de pagos en los módulos inspeccionados; `sales/payment.model.js` representa cobros operativos del ERP, no suscripciones SaaS.
2. Stripe Checkout y Billing Portal son el proveedor técnico seleccionado. La implementación utiliza HTTPS y API versionada `2024-06-20`; su compatibilidad debe validarse con la cuenta de prueba antes de publicar. Referencias oficiales: [Checkout](https://docs.stripe.com/api/checkout/sessions), [firmas y cuerpo original](https://docs.stripe.com/webhooks/signature), [suscripciones y eventos](https://docs.stripe.com/billing/subscriptions/webhooks). No se usaron transacciones reales.
3. El catálogo contiene un plan inicial, una moneda y periodo elegidos por configuración. Monedas soportadas inicialmente: MXN/USD/EUR, todas con dos decimales. No se infiere un precio; `COMMERCIAL_AMOUNT_MINOR` vacío deshabilita checkout. Los 10000 centavos de fixtures y preview son ficticios, exclusivamente para pruebas.
4. Usuarios: límite configurable positivo, inicialmente 5. Recursos operativos: explícitamente ilimitados (`null`) para productos, movimientos y proyectos. Sin periodo de gracia. Cancelación al final del periodo. No hay borrado automático; conservación, exportación y tratamiento fiscal definitivos pendientes de aprobación.
5. Se separan permisos de rol, módulos del plan, pagos confirmados, vigencia de contrato y existencia/configuración de empresa. SUPER_ADMIN no puede contratar ni aceptar invitaciones; ADMIN de empresa no obtiene privilegios de plataforma.
6. El registro público rechaza `role`, `companyId` y `permissions`. El modo privilegiado existe únicamente para desarrollo/tests, nunca staging/producción. El correo es único después de trim y lowercase; no se alteran puntos o aliases específicos de Gmail. Se exige confirmación de contraseña y versión exacta de términos.
7. MongoDB debe soportar transacciones (replica set o cluster sharded). Registro, verificación, activación, aceptación de invitación y configuración usan transacciones. Sin soporte transaccional no se degrada silenciosamente a escrituras parciales. Los índices de cuenta, tokens, eventos, invoice, sesión y membresía aportan idempotencia.
8. Una cuenta puede ser miembro de varias empresas, con empresa actual guardada en el usuario para reutilizar el ERP existente. `CommercialMembership` conserva roles por empresa y las membresías anteriores al activar una empresa adicional. Una contratación pendiente por propietario evita compras paralelas accidentales. No se reconfiguran ni cobran empresas heredadas automáticamente.
9. Invitaciones: rol inicial fijo VENTAS, siete días, correo verificado requerido. Reserva del último cupo mediante actualización condicional dentro de una transacción. No se liberan cupos automáticamente al cambiar de empresa ni se permite alterar roles vía campos de invitación.
10. No se acepta activación por URL de retorno. El webhook conserva cuerpo original, comprueba HMAC SHA-256 y tolerancia temporal de cinco minutos. Se consulta el snapshot actual del proveedor; se validan precio, moneda, cantidad, metadata, referencia, factura y suscripción. Un lease de reconciliación evita escribir snapshots simultáneos del mismo contrato. Ninguna llamada de red ocurre dentro de transacciones DB.
11. Reembolsos y disputas restringen acceso conservadoramente y requieren revisión de soporte. No se ejecutan reembolsos por API del ERP. Limpiar una retención no sustituye comprobar el estado del proveedor; la reconciliación puede mantener la restricción. Falta validación real de estos eventos.
12. Correo: outbox privado en MongoDB; tokens almacenados como hash en la entidad Token, enlaces secretos presentes solo en el mensaje pendiente. Resend como transporte configurable, con reintentos e idempotencia. En desarrollo sin credenciales el correo permanece en outbox; solo tests exponen resetToken por respuesta para compatibilidad con pruebas. En producción se exige remitente, URL HTTPS y credencial. [API oficial de Resend](https://resend.com/docs/api-reference/emails/send-email).
13. El frontend usa rutas por fragmento para conservar la navegación existente sin introducir dependencias. Cloudflare recibe `_redirects` y `_headers`. Los términos mostrados son un borrador, no aprobados; el contacto comercial no se inventa.
14. Se conserva el almacenamiento de sesión web existente en localStorage. Migrar a cookies HttpOnly / estrategia móvil segura requiere revisión adicional antes de habilitar comercialmente. No se añaden secretos de proveedor al frontend.
15. La exportación amplia de datos fue rechazada por revisión automática de permisos por incluir descarga de registros sensibles. No se aplicó ese exportador ni se ejecutó ninguna descarga. Queda pendiente autorización adicional para concretar campos, roles y formato.
16. El harness de MongoMemoryServer seleccionaba puertos reservados de Windows y abortaba con EACCES. `tests/mongo-ports.js` recupera exclusivamente ese error con un puerto elegido por el sistema operativo; los demás errores y todas las aserciones permanecen intactos.
17. Contraseñas nuevas: mínimo ocho caracteres, máximo 72 bytes UTF-8 (límite real bcrypt). Reset/cambio incrementan tokenVersion; refresh rota mediante compare-and-set.

## Propuesta de exportación pendiente de autorización

No aplicada. Descarga JSON paginada, máximo 100 registros por solicitud, únicamente por ADMIN verificado de la empresa actual, incluso con suscripción restringida. Allowlist propuesta: empresa/sucursales, productos, CRM, inventario, ventas/compras, finanzas, RRHH, proyectos/producción y membresías. Cada consulta exige companyId del contexto autenticado; nunca un identificador libre del navegador. Cursor validado y sin filtros arbitrarios. Excluye contraseñas, hashes, tokens, outbox, claves, cuerpos de webhook y otras empresas. Auditoría EXPORT sin contenido sensible; no envío a terceros ni almacenamiento externo. Requiere autorización adicional porque la revisión automática rechazó implementar la descarga amplia de registros sensibles.

## Pendientes de producto y revisión

Precio definitivo, nombre del plan, moneda/periodo definitivos, contacto comercial, texto legal aprobado, reglas fiscales y CFDI, políticas de retención/exportación y SLA. Los comprobantes de Stripe no se presentan como facturas fiscales mexicanas. No se habilitan cobros de producción mientras falten configuración, aprobaciones y validaciones críticas.
